# Резервы производительности — 2026-10-25

Источник: локальный `out/switch_logs/latest/ds2_085.log` (2026-10-24, «spike2»),
код текущего master. Попытка получить свежие логи по FTP 2026-10-25: timeout через 8 с.
Статистика пересчитана из лога; код и конфиг игры не менялись, запусков не было.

## 1. Кэш чтений: первый кандидат для уменьшения задержек подгрузки

Последний отчёт `range-cache` (16:28:14): 0 hits / 2 misses, 2 записи, 1 МБ из 64 МБ,
0 вытеснений; 6834 запроса ниже порога 256 КБ. Увеличивать ёмкость сейчас бессмысленно.
Существующий порог и комментарии в `sdk/src/filesystem/devices/host_path_file.cpp`
подбирались под другую игру (гонку), а не под SotFS.

В логе 17 медленных повторных чтений GameData1.bdt: все меньше 256 КБ,
суммарно 720,2 мс внутри чтений, максимум 64,7 мс. Среди них четыре запроса по 48 байт,
четыре по 131024 и три по 131072 байта. Это время потока IO, не доказанные потери времени
кадра; суммарное время нельзя переводить напрямую в выигрыш fps.

Следующий эксперимент: тот же NRO, ограниченная ёмкость 64 МБ, порог
`sa2_io_ranges_min_kb = 64`, повторить маршрут туда и обратно. Проверять hits/misses,
вытеснения, RAM, время чтений и кадры подгрузки. Порог 128 КБ пропустит запросы 131024 байта.
Мелкие заголовки (48 байт) останутся вне кэша; для них отдельно оценить хранение метаданных.
Также учитывать порядок путей: read-ahead обслуживает мелкие запросы до exact-range cache.
Не включать старый блочный кэш: его усиление чтений уже давало отрицательный результат.

## 2. Переходы освещения: световой зонд и операции EDRAM

36 кадров `[hitch]`, медиана 71,85 мс, максимум 375 мс. Из них 16 кадров с >=300 копированиями:
медиана 68,9 мс, максимум 91,4 мс. В конце лога такие кадры тратят на текстуры лишь 1,8–3,4 мс:
ускорение раскладки текстур не устранит этот класс провалов.

Предыдущий профиль ds2_084 указывает на AcquireNextImage и сброс meta-объектов NVK;
это выборка стеков, не доказательство первопричины. В `TargetsVulkan::BeginRecording`
сбрасываются два пула команд после Complete. Сначала нужны отдельные замеры ожидания
слота, сбросов пулов, acquire и CPU-readback зонда. Затем выбирать сокращение/объединение
копирований и резолвов либо работу с пулами. Простое уменьшение разрешения уже не помогло fps.

Метки относятся ко всему проходу и шейдерам его первой отрисовки: это не индивидуальная
стоимость PS. Таблица охватывает и загрузку, и игру, а лог перечисляет ограниченное число
проходов. Для изменения шейдеров сначала выделить одинаковый вид с упором в GPU на 720p,
разметить отрисовки внутри прохода, затем делать вариант за ключом и сравнивать картинку.
Дополнительно измерить FXAA: сейчас его цена вне меток GPU.

## 4. Остальные резервы

- Подготовка текстур после fused untile всё ещё стоит ~20 мс на 22–26 МБ (из журнала).
  Поток подготовки имеет смысл после проверки времени жизни гостевых данных: предыдущая
  попытка фонового копирования вершин была небезопасна. Разбивка на кадры может задержать LOD.
- Перепроверки стабильных текстур, memcpy и разбор пакетов — по свежему CPU-профилю
  точного ELF «spike2», а не по профилю прежнего NRO.
- deko3d остаётся большим отдельным проектом; текущие данные не позволяют обещать прирост.

Практический порядок: кэш мелких чтений → измерения светового зонда/пулов → GPU-проходы
на фиксированном виде. Для устойчивых fps на 720p приоритет у GPU; для подгрузки — у IO
и подготовки текстур. Ни один новый выигрыш этим аудитом не проверен.
