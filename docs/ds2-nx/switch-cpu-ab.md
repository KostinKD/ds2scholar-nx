**Статус: закрыт 2026-10-19 — прирост FPS не обнаружен, остаётся baseline (`ds2_pgouse`), ключ OFF.**

Дата: 2026-10-19. Цель — проверить `-fomit-frame-pointer` только в перекомпилированном коде игры.
Сборка и структурные проверки завершены; запуск и FPS на консоли ещё не проверены.

## Готовый пакет

Архив: `out/nx/cpu_ab/omitfp/ds2_cpu_ab_omitfp.zip`.
Распакованная папка: `out/nx/cpu_ab/omitfp/switch/ds2-nx/`.

Сохранить свой `ds2.toml`, затем скопировать содержимое папки `switch/` из архива на SD.
Используется уже имеющаяся `sdmc:/switch/ds2-nx/game_root/` с файлами игры.

- `ds2_baseline.nro`: проверенная сборка, метка версии в меню `cpu-baseline`.
- `ds2.nro`: новый эксперимент, метка `cpu-omitfp`.

- `sa2_shaders.mesp` и `.idx`: тот же пакет v14.

Первый запуск эксперимента — проверка загрузки, картинки и управления. Затем выполнить одинаковые прогоны,
описанные ниже. Обе NRO находятся в одной папке и используют общий конфиг и файлы игры.

## Конфиги

Подготовлены в `out/nx/cpu_ab/omitfp/configs/`. Для использования выбранный файл копируется как
`sdmc:/switch/ds2-nx/ds2.toml` перед запуском. Обе сборки читают один и тот же конфиг.

| Файл | Назначение |
|---|---|
| `ds2_diagnostic.toml` | точная копия текущего конфига Claude: info-лог, GPU marks, сбор missing shaders |
| `ds2_measure.toml` | логирование, GPU marks, shader dumps и отчёт enhancements выключены; лёгкий FPS/CPU report включён |
| `ds2_quiet.toml` | как measure, но `switch_profile_report=false`; измерение внешним FPS-счётчиком |

Во всех вариантах сохранены одинаковые графические настройки, GPU-wait sleep, нативный memcpy и отключение
межкадрового texture cache. Stack sampling выключен явно.
В measure FPS и реальные частоты пишутся в `logs/rex/rex_profile.log`, даже когда `log_level="off"`.
В quiet этот файл не обновляется: для FPS нужен внешний счётчик.

## Порядок теста

1. Использовать ту же консоль, режим, частоты, разрешение, сейв и положение камеры.
   Выбрать костёр Междумирья и отдельный тяжёлый участок Хейде.
2. Сначала baseline с diagnostic, затем baseline с measure: это цена диагностики, а не эффект компилятора.
3. Дальше обе сборки запускать только с одинаковым measure-конфигом: baseline → omitfp → baseline → omitfp.
   Повторить минимум три раза на вариант, по 2–3 минуты в одной сцене после прогрева.
4. В начале не двигаться 30–60 секунд; затем проходить один короткий маршрут и одинаково поворачивать камеру.
   Меню, загрузку и первые появления новых эффектов оценивать отдельно.
5. После каждого прогона сохранять `logs/rex/rex_profile.log` на PC под отдельным именем:
   `baseline_measure_1.log`, `omitfp_measure_1.log` и т. д. Файл перезаписывается при следующем запуске.
6. Сравнивать одинаковые игровые интервалы, реальные частоты и поведение картинки. При внешнем захвате времени
   кадров сравнить median/p95/p99 и долю кадров >33.3/>50 мс. Десятисекундный FPS-report не содержит полного
   распределения времени каждого кадра.

Разбор присланных логов (положить в одну папку, имена `<вариант>_*.log`):

```powershell
& tools\win\run.ps1 -Log logs\ab_omitfp.log -Cmd 'python -I tools/ab_profile_compare.py <папка>/*.log --skip-s 90 --min-cpu 200 --elf baseline=out/nx/keep/codex_omitfp_baseline/ds2.elf --elf omitfp=out/nx/keep/ds2_omitfp.elf'
```

Скрипт сам определяет сборку по размеру кода в первой строке лога (baseline 0x5642000, omitfp 0x55B3000)
и предупреждает, если имя файла с ней не совпадает или частоты менялись во время прогона.
`--skip-s` считает накопленное время: заголовок `==== 10.0 s` — длина интервала, а не время от старта.
`--min-cpu 200` отбрасывает меню (~70 % CPU) и оставляет мир (250 %+).

## Структурная проверка

`tools/check_switch_build.py` получил режим сравнения с проверенным на консоли ELF.
Он принимает только уже имеющиеся у эталона guest halt-функции и не допускает дополнительных
векторных FMA относительно эталона в каждой функции. Обычный строгий режим без reference остаётся доступен.
`--require-fewer-frame-pointers` проверяет, что эксперимент действительно сократил число игровых функций
с frame pointer. Эти проверки не заменяют запуск на Switch и проверку изображения.

```powershell
& tools\win\run.ps1 -Log logs\check_omitfp.log -Cmd 'python tools/check_switch_build.py --elf out/nx/ds2 --nro out/nx/ds2.nro --reference-elf out/nx/keep/codex_omitfp_baseline/ds2.elf --require-fewer-frame-pointers --sdk-vulkan G:/DS2Switch/mesa-switch/mesa-unified-install/opt/devkitpro/portlibs/switch/lib/libvulkan.a'
```

До новых экспериментов сначала сохранить окончательные NRO, ELF, конфиг и результаты этого A/B.
Следующий независимый опыт — настройки PGO-inliner; его не надо смешивать с проверкой frame pointer.

## Скорость сборки

Ссылка по-прежнему сообщает `using serial compilation of 512 LTRANS jobs`, хотя в link flags есть `-flto=2`.
В использованном окружении `where make` ничего не находит, переменная `MAKE` не задана

с тем же окружением этого не меняет. Эта настройка в текущем A/B не применялась.

# CPU A/B: второй эксперимент — лимиты PGO-инлайнера

Дата: 2026-10-19. Как в SA2 (`../sa2-nx/docs/cpu-rounds.md`, «The link with the new profile»): для кода игры
при `DS2_PGO=use` поднять `max-inline-insns-auto` 30 → 64 и ограничить `inline-unit-growth` 40 → 12 %.
В SA2 это сократило исполняемые вызовы на 41 %, оценка времени GCC −1.5 %, горячий код +17 %.

Новые ключи CMake (по умолчанию пустые = проверенная сборка): `DS2_SWITCH_INLINE_AUTO`,
`DS2_SWITCH_INLINE_UNIT_GROWTH`, `DS2_SWITCH_LTO_DUMP` (дамп `-fdump-ipa-inline` и `out/nx/ds2.map` для
`tools/lto_inline_report.py`; код от дампа не меняется). Профиль PGO тот же (pgo/), параметры инлайнера его не
затрагивают. Остальное — как у `ds2_pgouse`, omitfp OFF.

```powershell
& tools\win\run.ps1 -Log logs\configure_inline64.log -Cmd 'cmake -S app -B out/nx -DDS2_SWITCH_INLINE_AUTO=64 -DDS2_SWITCH_INLINE_UNIT_GROWTH=12 -DDS2_SWITCH_LTO_DUMP=ON -DDS2_SWITCH_OMIT_FRAME_POINTER=OFF -DDS2_SWITCH_LTO=ON -DDS2_PGO=use -DDS2_SWITCH_IPA_PTA=OFF -DDS2_SWITCH_HOT_ORDER=OFF -DDS2_GUEST_VOLATILE=OFF'
& tools\win\run.ps1 -Log logs\build_inline64.log -Cmd 'powershell -NoProfile -ExecutionPolicy Bypass -File tools\win\build_switch.ps1 -Jobs 8'
```

svcSleepThread «up to 1 ms»: 53 000/с, 2.05 s/с). Что именно эти паузы дают основную долю счётчика — вывод

# Диагностика: время ожиданий каждого потока (`switch_profile_waits`)

После трёх опытов без прироста (omitfp, inline64, naps0) вопрос — какое звено цепочки кадра кого ждёт. CPU % и
выборка стеков раз в 1 мс этого не разделяют.

## Как отображена память игры на Switch (чтение кода, 2026-10-19)

sdk/src/core/guest_memory_switch.cpp: окно 4.5 ГБ зарезервировано с выравниванием 2 МБ; память выделяется чанками
гранулами 2 МБ (`memalign(2 МБ)` из кучи → code alias `svcMapProcessCodeMemory` → `svcMapProcessMemory` в каждый вид
при первом обращении). Это позволяет ядру отобразить гранулу одним блоком 2 МБ (одна запись TLB вместо 512), если
физическая память непрерывна — из пользовательского режима не видно.

Что ломает блоки:
- ядро отказало в смене прав на страницах окна (`watching: unmapping` в профиле), поэтому «защита» = вырезание
  страницы из окна;
- на Switch `Memory::Decommit`/`Release` гостевых куч — тоже `RexGmProtect(NONE)` (memory_switch.cpp:206), то есть
  обычное освобождение памяти игрой режет гранулы;
- снятие защиты отображает страницы обратно по одной (`svcMapProcessMemory` по 4 КБ) — склеит ли ядро гранулу
  обратно в блок, неизвестно.

Диагностика (под `switch_profile_waits`, строка `guest pages:` в отчёте): МБ в целых гранулах, никогда не
разрезанных / с защищёнными страницами сейчас / разрезанных раньше и отображённых обратно по страницам; МБ вне
целых гранул и невыровненные. Учёт разрезанных гранул (`split_granules`) ведётся всегда — вставка в std::set при
каждом снятии отображения страницы, рядом с svc. Сборка: logs/build_pages.log.
Собрано: `out/nx/keep/ds2_pages.nro` (SHA256 `7050DA52…5BF3D616`) / `.elf`, проверка против baseline пройдена
(logs/check_pages.log). Пакет `out/nx/cpu_ab/pages/switch/ds2-nx/` (ds2_pages.nro, метка `cpu-pages`, + ds2.toml
с `switch_profile_waits = true`). На консоли не проверено.

RexGmCommit для чанков ≥ 2 МБ). Физическая непрерывность кучи по-прежнему не видна из пользовательского режима;
