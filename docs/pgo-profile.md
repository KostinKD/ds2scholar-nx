# PGO v4 для пользовательской сборки

Профиль владельца можно использовать на другой Windows-машине с
devkitA64 GCC **16.1.0**, той же Xbox 360 SotFS и совместимыми исходниками.
Собирать свои игровые сессии для этого необязательно.

После установки пакета используйте `tools/win/rebuild_switch.ps1`:
[настройка и повторная сборка](rebuild.md).

Пакет `ds2scholar-nx-pgo-v4-1.10.0-access1.zip` — отдельный вход сборки:
364 GCDA (6 553 988 байт), manifest с SHA256 и `codegen.partition.json`.
Таблица распределения функций нужна для воспроизведения профиля после
чистого кодогена. C++, XEX, игровые ресурсы, NRO и raw stream в ZIP не входят.
ZIP и его содержимое не хранятся в Git; подготовленный файл — в `out/release/`.

**Совместимая база:** начальный коммит `master`, отмеченный тегом `v1.10.0-access1`.
Точный SHA записан в `manifest.json` нового PGO ZIP; старая история не требуется.
Допускаются дальнейшие изменения документации и инструментов упаковки;
изменения игровых/SDK/кодоген-входов требуют новой проверки совместимости.
Установщик проверяет исходники относительно этой базы и версию компилятора.
Это ограничение проверенного пакета; оно не означает несовместимость GCC
других версий со всеми PGO вообще.

## Установка

В релизной ветке исходники HOME-forwarder, упаковщика и диагностической NRO
не инвалидируют профиль игры: они исключены точными путями из проверки GCC-входов.
Изменения app/sdk и кодогена по-прежнему отклоняются. Проверка 5 ноября:
установка364 GCDA/4 перенесённых путей в отдельную папку,6553988Б; содержимое
всех профилей совпало с ZIP. Существующий профиль владельца не заменялся.

Из корня клона с инструментами этой ветки (Python 3.10+):

```powershell
$env:SA2_LLVM = 'G:\Program Files\LLVM'
$env:SA2_VSDIR = 'G:\Program Files\VisualStudio'
$env:DEVKITPRO = 'G:/devkitPro'

tools/win/run.ps1 logs/pgo_install.log "python -I tools/pgo_bundle.py install <путь-к-ZIP>"

# Нужны собранный host-генератор и своя игра, см. clean-build.md.
tools/win/run.ps1 logs/codegen.log "powershell -NoProfile -ExecutionPolicy Bypass -File tools/codegen.ps1 -Flavor optimised"
tools/win/run.ps1 logs/pgo_build.log "powershell -NoProfile -ExecutionPolicy Bypass -File tools/win/build_switch.ps1 -Jobs 5 -Reconfigure -BuildDir out/nx_pgo -Define DS2_PGO=use,DS2_SWITCH_LTO=ON"
```

Установщик создаёт `pgo/`, переносит четыре абсолютных имени GCDA на ваш путь
и подготавливает `app/generated/default/codegen.partition.json`. Содержимое
GCDA не меняется. Прежняя отличающаяся таблица сохраняется в
`out/pgo-layout-backups/`. Если `pgo/` уже существует, установка отказывается
его перезаписывать; сохраните свой профиль отдельно перед установкой.

**Устанавливайте пакет перед кодогеном.** После установки повторный кодоген
обязателен даже при наличии старых `app/generated/`: одной замены имён GCDA
недостаточно. Для повторной подготовки таблицы из уже установленного пакета:

```powershell
python -I tools/pgo_bundle.py prepare-codegen
```

Проверка реального применения профиля без ссылки NRO:

```powershell
tools/win/run.ps1 logs/pgo_fit.log "python -I tools/pgo_fit.py --build-dir out/nx_pgo --all --jobs 5 --strict-guest"
```

Проверяются все C++-объекты с PGO, предупреждения GCC включены. Отдельно
считаются отсутствующие GCDA, потери гостевых функций и вспомогательных
функций, а также изменение расположения исходников без потери CFG-профиля. Полный `--strict`
дополнительно запрещает потери вспомогательных функций. Результаты и полные
диагностики — в `out/pgo_fit/<имя-build-dir>/`.

При изменении профиля в ранее собиравшемся `out/nx_pgo` нужен `clean` перед
пересборкой: Ninja сам не отслеживает содержимое GCDA. Отдельный новый build-dir
не требует очистки.

## Подготовка пакета владельцем

```powershell
tools/win/run.ps1 logs/pgo_pack.log "python -I tools/pgo_bundle.py pack --source-revision v1.10.0-access1 --output out/release/ds2scholar-nx-pgo-v4-1.10.0-access1.zip"
```

Используются существующие `pgo/` и таблица кодогена. Архив не перезаписывается;
для другой ревизии нужен новый выходной файл. Хеши проверяются до установки.

## Историческая проверка исходного профиля 2026-11-03

Хеш и размер ниже относятся к прежнему ZIP. В релизе обновлено только поле
исходной ревизии manifest; все364 GCDA и таблица кодогена сохранены побайтово.

Профиль v4: игровая сессия 29 октября (4,5 мин), 364 GCDA, GCC16.1.0.
Пакет установлен в `out/clean-clone-20261103/pgo_v4_portable`, исходный
`pgo/` владельца сохранён. SHA256 ZIP:
`CD74D7E6E442B2446D96A5A5623999580ED9C66668B9BEC4584ECC96579FD39D`,
размер 2 321 302 байта.

После повторного кодогена (355,8с,334 файла recomp) GCC проверил366 объектов
с PGO:84296 гостевых определений,0 ошибок компиляции,0 отсутствующих GCDA,
0 потерянных/отсутствующих гостевых профилей. Компиляция без LTO и без PCH,
с настоящим чтением GCDA, заняла18мин17с. Дополнительная проба профиля и
build-dir с пробелами:325 гостевых определений и host-шаблоны Draw,exit0,
гостевых потерь0. Тесты упаковки/диагностики:19/19,exit0; результаты —
`logs/pgo_tools_tests_final.log`.

**Ограничение:**1179 случаев отсутствующего профиля вспомогательной функции
по объектам (не число уникальных функций всей программы); ещё3 несовпадения
CFG — `Start/DumpNow/Stop` в ds2_pgo.cpp, где generate/use выбирают разные
ветки `DS2_PGO_GENERATE`. Для этих функций профиль не используется;
полный `--strict` не проходит. Пакет не обещает стопроцентного переноса
вспомогательного кода или прежнего FPS. Полный PGO NRO, его запуск и A/B
этого переноса на консоли пока не подтверждены.

Первичный полный прогон (`logs/pgo_relocated_all.log`) сохранил exit1:
первый классификатор ошибочно принял3 шаблонных параметра
`Draw<__imp__sub_…>` за имена гостевых функций. Регрессионный тест сначала
воспроизвёл ошибку; после исправления все сохранённые GCC-диагностики повторно
разобраны текущим классификатором, без изменения входов компилятора:
`logs/pgo_relocated_reanalyzed.log`,exit0;
`out/pgo_fit/nx_pgo_verify/report.reanalyzed.json`. Первичный лог не переписан.
Новая настоящая компиляция пробы с пробелами выполнена уже после исправления
(`logs/pgo_space_compile.log`,exit0). Повторная упаковка даёт тот же SHA256.

Причина дополнительной таблицы доказана пробой: при чистом распределении
`sub_83391DE0` попала в recomp.0 вместо recomp.258; все293 функции пробного
recomp.0 не нашли свои записи. В исходном дереве проба recomp.0 дала325
функций и0 потерь. Имена GCDA уже были перенесены правильно в обоих случаях.
Механизм поиска GCC описан в [coverage.cc](https://raw.githubusercontent.com/gcc-mirror/gcc/master/gcc/coverage.cc)
(`read_counts_file`, `get_coverage_counts`); предупреждение Wmissing-profile
может относиться как к целому файлу, так и к отдельной функции.
